# Professional Frontend Design

Create frontend interfaces that feel deliberately designed by a professional UI/UX designer rather than assembled from generic AI-generated patterns.

The goal is not to make the interface visually complicated.

The goal is to make it:

- clear
- refined
- balanced
- functional
- memorable
- responsive
- pleasant to use
- visually consistent
- appropriate for the product

Prioritize:

1. Clarity
2. Visual hierarchy
3. Usability
4. Consistency
5. Restraint
6. Responsiveness
7. Accessibility
8. Meaningful interaction
9. Subtle motion
10. Strong visual identity

Avoid adding visual elements simply because they are technically possible, fashionable, or commonly generated by AI.

When in doubt, simplify.

---

# Design Philosophy

## Design With Intention

Every visual element should have a reason to exist.

An element should primarily serve at least one meaningful purpose:

- communicate information
- establish hierarchy
- guide attention
- improve navigation
- provide feedback
- establish visual identity
- improve usability
- support an interaction
- separate related or unrelated content

If an element does not provide a meaningful purpose, consider removing it.

Prefer:

> better composition over more decoration

and:

> clearer hierarchy over more components

---

# Avoid Generic AI Design

Do not automatically use common AI-generated visual patterns such as:

- excessive rounded cards
- excessive pill-shaped controls
- huge gradients
- random purple or blue gradients
- glassmorphism everywhere
- floating blobs
- excessive glow effects
- excessive shadows
- cards inside cards inside cards
- every section enclosed in a container
- every element given a border
- giant headings without useful supporting content
- excessive icons
- decorative illustrations that communicate nothing
- excessive use of `rounded-full`
- excessive use of `rounded-2xl`
- making every button a pill
- making every element appear to float
- excessive use of badges
- excessive use of gradient text
- excessive background decoration
- excessive animation
- excessive parallax
- arbitrary neon accents
- randomly generated dashboard widgets
- unnecessary statistics
- fake testimonials or decorative content
- components added solely because they look "modern"

Do not assume:

> modern = rounded + gradient + glass + shadow + animation

A professional interface can be quiet, restrained, sharp, and extremely polished.

---

# Visual Restraint

Professional design depends heavily on knowing what not to add.

Before adding a visual element, ask:

1. Does it improve understanding?
2. Does it improve usability?
3. Does it establish hierarchy?
4. Does it communicate state?
5. Does it strengthen the product's identity?
6. Does it improve interaction?

If the answer is no, consider removing it.

A visually sophisticated interface often contains fewer elements than an inexperienced design.

---

# Design Language

Establish a visual language before building many components.

Define:

- color
- typography
- spacing
- geometry
- borders
- shadows
- iconography
- motion
- interaction states
- visual density

The design language should remain consistent throughout the application.

Do not independently style every page.

---

# Geometry and Shape

Use geometry intentionally.

The interface should feel:

- clean
- controlled
- sharp where appropriate
- smooth where appropriate
- consistent
- balanced

Do not make every component heavily rounded.

Corner radius should communicate the character of the product.

Use different levels of radius deliberately.

For example:

- small radius for compact controls
- moderate radius for containers
- larger radius for intentionally prominent surfaces
- circular shapes for genuinely circular elements
- minimal or no radius where a sharper appearance is more appropriate

Do not use one radius value for every element.

Avoid blindly applying:

```text
rounded-full
rounded-2xl
rounded-3xl
````

to everything.

---

# Sharp and Smooth

Sharp and smooth are not opposites.

A professional interface can combine:

* sharp structural containers
* subtle corner rounding
* smooth transitions
* clean typography
* controlled spacing
* precise alignment

The desired aesthetic is:

> sharp in structure, smooth in interaction.

Do not interpret "sharp" as making every element completely square.

Do not interpret "smooth" as making everything heavily rounded.

---

# Spacing

Whitespace is part of the design.

Use spacing to establish:

* grouping
* hierarchy
* rhythm
* focus
* separation
* readability

Do not fill empty space simply because it exists.

Prefer:

```text
intentional whitespace
+
strong alignment
+
clear hierarchy
```

over:

```text
more cards
+
more borders
+
more decorations
```

Use a consistent spacing scale.

Related elements should generally be closer together.

Unrelated sections should have stronger separation.

---

# Alignment

Alignment should feel intentional.

Pay attention to:

* left edges
* right edges
* vertical alignment
* baseline alignment
* container widths
* button alignment
* input alignment
* navigation alignment
* card content alignment

Avoid layouts where elements appear randomly positioned.

A clean alignment system often makes an interface feel more professional without adding any decoration.

---

# Layout

Design layouts around user goals.

Before choosing a layout, determine:

* what the user needs to see first
* what action the user needs to take
* what information is supporting information
* what information can remain secondary
* how often the user interacts with the screen

Do not use a grid simply because grids are easy to generate.

Do not create dashboard cards just to fill available space.

Use:

* columns
* sections
* dividers
* whitespace
* lists
* tables
* navigation
* panels

when they communicate the content better.

---

# Visual Hierarchy

Every screen should have a clear hierarchy.

The user should quickly understand:

1. Where they are
2. What the screen is about
3. What is most important
4. What action is expected
5. What information is secondary
6. What state the system is currently in

Do not make every element compete for attention.

Use:

* typography
* size
* weight
* position
* spacing
* contrast
* color
* borders
* motion

to establish hierarchy.

Do not rely on color alone.

---

# Primary Focus

Each screen should have a primary focus.

Examples:

```text
Dashboard
→ important information and actions

Form
→ completing the form

Details page
→ understanding the selected record

Search page
→ finding the requested information

Settings
→ configuring the system
```

Do not make every section equally prominent.

---

# Color System

## Ask for the Color Palette

When beginning a new frontend design, ask the user for the desired color palette when the project does not already have an established visual identity.

If the user provides colors, use them as the foundation.

If the project already has established colors, inspect and preserve them rather than asking again.

If the user does not care about colors, propose a professional palette appropriate to the product.

Do not repeatedly ask for the palette once a clear visual system has already been established.

---

# When Two Main Colors Are Provided

If the user provides two primary colors, do not simply alternate those two colors throughout the interface.

Build a complete palette around them.

Create appropriate roles such as:

* primary
* primary hover
* primary active
* primary subtle
* secondary
* secondary hover
* secondary active
* secondary subtle
* accent
* background
* surface
* elevated surface
* border
* divider
* strong text
* normal text
* secondary text
* muted text
* disabled
* success
* warning
* error
* informational

Use:

* tints
* shades
* tones
* neutrals
* controlled opacity

to create a coherent system.

Not every derived color should be highly saturated.

---

# Color Hierarchy

Do not use the primary brand color on everything.

Brand colors should establish:

* identity
* emphasis
* important actions
* active states
* navigation state
* important information

Use neutrals for most of the interface when appropriate.

A professional interface often uses brand colors sparingly.

---

# Backgrounds

Backgrounds should support hierarchy.

Use background variations to distinguish:

* page
* section
* surface
* elevated content
* selected content

Do not create multiple background colors without a purpose.

Avoid strong gradients behind every section.

---

# Gradients

Gradients are optional.

Use them only when they contribute meaningfully to:

* branding
* depth
* emphasis
* visual atmosphere

Avoid random gradients added solely because they look "modern."

Do not use a gradient on:

* every button
* every card
* the entire page
* every heading

---

# Contrast

Maintain sufficient contrast between:

* text and background
* controls and background
* borders and surfaces
* selected and unselected states
* disabled and active states

Do not sacrifice readability for aesthetic minimalism.

---

# Typography

Typography should establish hierarchy before decoration does.

Define a deliberate type scale.

Consider:

* display
* page title
* section heading
* subsection heading
* body
* label
* caption
* navigation
* metadata
* helper text

Do not make everything bold.

Do not make every heading enormous.

Use:

* size
* weight
* line height
* letter spacing
* color
* spacing

together.

---

# Font Selection

Choose typography according to:

* product personality
* readability
* platform
* language
* density
* brand identity

Do not automatically use the same fashionable font for every project.

The font should support the interface rather than become the interface.

---

# Typography Consistency

Maintain consistent:

* heading sizes
* body sizes
* line heights
* font weights
* label styles
* metadata styles

Do not introduce arbitrary typography values throughout the application.

---

# Text Density

Avoid excessive text where the interface can communicate information more efficiently.

However, do not remove useful information merely to make a page look minimal.

Minimalism is not:

> less information at all costs.

It is:

> presenting necessary information without unnecessary visual noise.

---

# Components

Components should feel like parts of one design system.

Maintain consistency across:

* buttons
* inputs
* cards
* navigation
* tables
* modals
* dropdowns
* tabs
* badges
* alerts
* tooltips
* empty states
* loading states
* error states

Components should share:

* geometry
* spacing
* typography
* color behavior
* interaction behavior
* motion language

Consistency does not mean every component must look identical.

---

# Reusable Components

Create reusable components when they represent a genuine repeated pattern.

Examples:

```text
Button
Input
Select
Modal
Table
DataRow
NavigationItem
Toast
Badge
EmptyState
LoadingState
```

Do not create abstractions so aggressively that simple UI becomes difficult to understand.

Avoid both:

```text
everything duplicated
```

and:

```text
one enormous component that controls the entire application
```

---

# Buttons

Buttons should communicate action hierarchy.

Establish levels such as:

* primary
* secondary
* tertiary
* destructive
* icon-only

Not every action should receive the same visual weight.

Primary actions should be visually dominant.

Secondary actions should remain available without competing with the primary action.

Destructive actions should communicate their consequences clearly.

---

# Button Shape

Do not make every button a pill.

Use the established geometry of the product.

Buttons can be:

* sharp
* lightly rounded
* moderately rounded
* circular for icon-only controls

depending on the design language.

---

# Button States

Buttons should have clear states:

* default
* hover
* focus
* active
* disabled
* loading
* success where appropriate
* error where appropriate

Do not rely only on color.

---

# Button Feedback

A button should communicate that interaction occurred.

Use subtle changes such as:

* background
* border
* opacity
* shadow
* icon movement
* slight scale
* text change

Do not make a button:

```text
jump
+
rotate
+
glow
+
scale
```

simultaneously.

One or two coordinated changes are usually enough.

---

# Forms

Forms should prioritize clarity and completion.

Use:

* clear labels
* appropriate grouping
* helpful descriptions
* visible validation
* clear required indicators
* appropriate input types
* logical tab order
* useful error messages

Do not hide essential instructions inside decorative elements.

---

# Input States

Inputs should have distinct:

* default
* hover
* focus
* filled
* disabled
* error
* success

states when relevant.

Focus should be visually obvious.

Do not remove focus indicators merely because they are visually inconvenient.

---

# Validation

Validation feedback should be:

* close to the relevant field
* understandable
* actionable
* visually distinct

Avoid vague messages such as:

```text
Invalid input
```

when a more useful explanation is possible.

---

# Forms and Loading

When submitting forms:

* communicate that submission started
* prevent accidental duplicate submissions
* preserve user input where possible
* show meaningful progress
* communicate success or failure

Do not make users wonder whether clicking the button worked.

---

# Cards

Use cards when they improve grouping or comprehension.

Do not put everything inside cards.

Avoid:

```text
Card
  └── Card
      └── Card
          └── Card
```

Use:

* whitespace
* dividers
* typography
* alignment
* background changes

when those communicate grouping more effectively.

---

# Tables

For administrative and data-heavy systems, tables may be better than cards.

Do not convert every record into a card simply because cards look more modern.

Prioritize:

* scanability
* alignment
* sortable columns
* readable density
* clear actions
* responsive behavior

Use row hover or selection states subtly.

---

# Dashboards

Dashboards should prioritize useful information.

Do not generate arbitrary:

* statistics
* charts
* graphs
* percentage indicators
* decorative widgets

just to make the dashboard look impressive.

Every dashboard element should answer a meaningful user question.

---

# Data Visualization

Charts should communicate information rather than decorate the page.

Use the appropriate visualization for the data.

Avoid:

* unnecessary 3D charts
* excessive gradients
* excessive animation
* too many colors
* charts without labels
* decorative graphs with no useful meaning

The chart should remain understandable without animation.

---

# Navigation

Navigation should make location and available actions clear.

Consider:

* active state
* hierarchy
* grouping
* labels
* icons where useful
* responsive behavior

Do not use icons as decoration when text is clearer.

---

# Sidebars

A sidebar should contain meaningful navigation.

Avoid:

* unnecessary nested levels
* excessive icon-only navigation
* excessive badges
* decorative sections

If collapsed navigation is used, ensure the user can still understand what each icon represents.

---

# Headers

Headers should establish:

* location
* context
* important actions
* account/session information

Do not fill the header with unnecessary controls.

---

# Modals

Use modals when the user needs to temporarily focus on a task or decision.

Do not use modals for everything.

Consider whether the interaction would be better as:

* inline content
* a drawer
* a dedicated page
* an expandable section

Avoid excessively large modal windows containing entire applications.

---

# Toasts and Notifications

Notifications should communicate meaningful events.

Use them for:

* successful actions
* recoverable failures
* important background events

Do not show a toast for every small interaction.

Avoid stacking so many notifications that they become distracting.

---

# Empty States

Empty states should explain:

1. what is empty
2. why it may be empty
3. what the user can do next

Avoid empty screens containing only:

```text
No data
```

When appropriate, provide a useful action.

---

# Loading States

Loading states should communicate what is happening.

Use:

* skeletons
* progress indicators
* subtle placeholders
* contextual loading text

where appropriate.

Do not show a spinner for every tiny interaction.

Avoid making the entire screen appear blocked when only one section is loading.

---

# Error States

Errors should be:

* understandable
* specific enough to be useful
* visually clear
* recoverable where possible

Provide actions such as:

* retry
* refresh
* go back
* correct input

when appropriate.

Do not expose technical stack traces to normal users.

---

# Animation and Motion

Motion should improve the experience.

Use animation to:

* communicate state changes
* provide feedback
* establish spatial relationships
* guide attention
* make transitions feel natural
* reinforce interaction
* give the product personality

Do not animate everything.

---

# Motion Language

A product should have a consistent motion language.

For example:

```text
small interaction
→ fast and subtle

modal
→ controlled entrance and exit

page transition
→ smooth and restrained

important state change
→ slightly more noticeable
```

Do not give every component a completely different animation style.

---

# Animation Characteristics

Animations should generally feel:

* smooth
* responsive
* natural
* controlled
* subtle
* intentional

Avoid:

* excessive bouncing
* constant floating
* long transitions
* dramatic movement
* excessive parallax
* unnecessary rotation
* animation that delays interaction
* animation used only to demonstrate technical capability

The user should primarily notice that the interface feels polished.

---

# Timing

Animation timing should reflect the importance and size of the interaction.

Small interactions should usually be faster.

Large transitions may require slightly more time.

Do not make users wait for decorative animation before they can continue using the application.

---

# Easing

Use natural easing.

Avoid overly mechanical movement.

The motion should feel intentional rather than like every element simply has a CSS transition attached to it.

---

# Hover States

Interactive elements should provide feedback where hover is available.

Possible changes include:

* background
* border
* opacity
* shadow
* text color
* icon movement
* subtle scale

Keep hover effects restrained.

Do not combine multiple dramatic effects.

---

# Focus States

Focus states are required for accessible keyboard interaction.

Use a clear but visually appropriate focus treatment.

Do not remove focus outlines without replacing them with an equally clear focus indicator.

---

# Active States

Users should be able to tell when an element is:

* selected
* active
* pressed
* expanded
* enabled

Use visual hierarchy rather than relying exclusively on animation.

---

# Micro-interactions

Use micro-interactions when they provide useful feedback.

Examples:

* button press
* input focus
* tab selection
* menu opening
* dropdown transition
* modal transition
* successful save
* loading completion
* toggle change
* copy confirmation
* row selection

Micro-interactions should reinforce the action.

---

# Scroll Animations

Use scroll-triggered animation when it meaningfully improves presentation.

Appropriate examples:

* hero entrance
* section reveal
* content grouping
* subtle image movement
* progressive appearance

Avoid animating every element independently.

Do not make the interface feel like a slideshow.

---

# Staggered Animation

When several related elements enter together, a small stagger can create visual rhythm.

For example:

```text
heading
↓
description
↓
action
```

Avoid long cascading delays.

The interface should become usable immediately.

---

# Reduced Motion

Respect:

```css
@media (prefers-reduced-motion: reduce)
```

Reduce or disable decorative animations when users request reduced motion.

Accessibility takes priority over visual effects.

---

# Responsiveness

Design for multiple screen sizes from the beginning.

Consider:

* mobile
* tablet
* laptop
* desktop
* large displays

Do not treat mobile as an afterthought.

---

# Responsive Layout

Responsive design should adapt structure rather than simply shrink everything.

Consider:

* changing columns
* reorganizing navigation
* resizing typography
* changing spacing
* stacking controls
* simplifying secondary information
* changing table behavior

Do not simply make a desktop layout narrower.

---

# Mobile Design

On mobile:

* prioritize important information
* maintain readable text
* maintain comfortable touch targets
* simplify dense interfaces
* avoid horizontal overflow
* avoid tiny controls
* preserve clear hierarchy

Do not remove important functionality solely because the screen is smaller.

---

# Touch Targets

Interactive controls should have appropriate touch areas.

Do not create tiny buttons simply to maintain visual minimalism.

The interface can remain visually minimal while still having comfortable interaction areas.

---

# Responsive Tables

For data-heavy applications, determine whether a table should:

* scroll horizontally
* collapse columns
* transform rows
* use a detail view
* prioritize essential fields

Do not force every desktop table into a cramped mobile layout.

---

# Accessibility

Professional design must also be usable.

Consider:

* semantic HTML
* keyboard navigation
* focus states
* color contrast
* screen reader support
* labels
* touch targets
* reduced motion
* meaningful error states

Never remove accessibility features merely because they make the interface slightly less visually minimal.

---

# Semantic HTML

Use semantic elements when appropriate:

```html
<header>
<nav>
<main>
<section>
<article>
<footer>
<button>
<form>
<label>
```

Do not use generic `<div>` elements for everything when semantic elements communicate meaning better.

---

# Keyboard Navigation

Ensure interactive interfaces can be used with a keyboard.

Consider:

* logical tab order
* visible focus
* keyboard activation
* modal focus management
* dropdown navigation
* escape behavior

Do not create custom interactions that work only with a mouse.

---

# Contrast

Check important text and controls for adequate contrast.

Do not use low-contrast gray text simply because it looks elegant.

Visual subtlety should never make information difficult to read.

---

# Icons

Use icons when they improve comprehension or interaction.

Do not add icons merely because the interface looks empty.

Icons should maintain:

* consistent style
* consistent weight
* consistent sizing
* consistent alignment

Avoid mixing unrelated icon styles.

---

# Icon-Only Controls

Icon-only controls should have clear meaning.

Provide:

* accessible labels
* tooltips where useful
* adequate touch area
* recognizable iconography

Do not assume every user understands an unfamiliar icon.

---

# Imagery

Images should support:

* content
* branding
* context
* storytelling

Do not use random stock imagery merely to fill space.

Avoid decorative imagery that competes with important information.

---

# Design References

When the user provides:

* a website
* screenshot
* design
* mockup
* visual example
* reference application

study the underlying visual principles.

Identify:

* spacing
* typography
* geometry
* color usage
* visual hierarchy
* animation
* interaction
* density
* composition

Recreate the design principles rather than blindly copying the interface.

Do not reproduce proprietary branding or content unnecessarily.

---

# Barrydev Reference

The website:

```text
https://barrydev.vercel.app/
```

is a reference for the desired level of frontend quality.

Use it as inspiration for:

* visual refinement
* restraint
* typography
* composition
* spacing
* interaction
* motion
* overall polish

It is a quality reference, not a template.

Do not blindly reproduce its exact layout, branding, or content.

Adapt the principles to the actual project.

---

# Existing Projects

When working on an existing project:

1. Inspect the current interface.
2. Identify the established design language.
3. Identify the existing colors.
4. Identify typography.
5. Identify spacing.
6. Identify component patterns.
7. Identify border-radius conventions.
8. Identify animation behavior.
9. Identify responsive behavior.
10. Preserve intentional design decisions.

Do not redesign everything simply because a different style is personally preferred.

Improve the interface while maintaining product consistency.

---

# Existing Design Systems

If the project already uses a design system or component library:

* understand its conventions
* reuse existing primitives when appropriate
* extend the system rather than fighting it
* avoid introducing unnecessary competing patterns

Do not replace a working design system without a clear reason.

---

# Framework Awareness

Implement the design according to the project's actual frontend stack.

For example:

* React
* React Native
* Vue
* Svelte
* Angular
* Next.js
* Vite
* Tailwind
* CSS Modules
* styled-components
* native CSS

Do not introduce unnecessary libraries simply to create a visual effect.

Prefer the project's existing tools when they can accomplish the design appropriately.

---

# React and Component Design

When working in React:

* keep components purposeful
* avoid unnecessarily large components
* reuse genuinely repeated UI
* separate concerns when complexity warrants it
* preserve predictable state behavior
* avoid visual duplication caused by inconsistent component implementations

Do not create dozens of tiny components when doing so makes the project harder to understand.

---

# Styling

Prefer a coherent styling system.

Avoid arbitrary values scattered throughout the project.

Maintain consistency in:

* spacing
* colors
* typography
* radius
* shadows
* transitions
* breakpoints

Where appropriate, define reusable design tokens.

---

# Design Tokens

For larger projects, consider centralizing:

```text
colors
spacing
font sizes
font weights
line heights
radii
shadows
transitions
breakpoints
z-index layers
```

This makes visual refinement easier and prevents inconsistent styling.

---

# Shadows

Use shadows to communicate meaningful elevation.

Prefer:

* subtle shadows
* controlled depth
* consistent elevation levels

Avoid:

* heavy shadows on every card
* glowing shadows
* multiple competing shadow levels

If a component does not need elevation, it may not need a shadow.

---

# Borders

Borders can communicate:

* grouping
* separation
* hierarchy
* interactive states

Do not give every element a border.

Sometimes whitespace is a better separator.

---

# Surface Hierarchy

Use surfaces deliberately.

For example:

```text
Page background
    ↓
Primary surface
    ↓
Elevated surface
    ↓
Focused/selected surface
```

Do not create dozens of surface variations.

---

# Z-Index and Layering

Layering should be intentional.

Establish predictable levels for:

* navigation
* dropdowns
* tooltips
* modals
* notifications
* overlays

Avoid arbitrary `z-index` values scattered throughout the application.

---

# Loading Experience

Loading should feel intentional.

Use:

* skeletons when structure is known
* progress indicators for measurable progress
* contextual messages for long operations
* optimistic feedback where appropriate

Do not block the entire application unnecessarily.

---

# Interaction Responsiveness

The interface should acknowledge user actions quickly.

When an action takes time:

```text
user action
↓
immediate feedback
↓
processing
↓
result
```

Do not leave the user staring at an unchanged button or screen.

---

# Frontend Data Behavior

When designing interfaces that communicate with APIs, consider:

* loading states
* error states
* empty states
* retry behavior
* request cancellation
* duplicate request prevention
* optimistic updates
* stale data
* background refresh
* polling
* streaming
* pagination

Use these patterns only when the project actually benefits from them.

Do not introduce complex data behavior simply because it is available.

---

# Performance

Visual quality should not come at the expense of performance.

Avoid unnecessary:

* large assets
* expensive animations
* excessive DOM elements
* repeated rendering
* oversized images
* unnecessary libraries
* continuous animation
* expensive effects

Prefer efficient implementation without sacrificing visual quality.

---

# Perceived Performance

The interface should feel responsive even when operations take time.

Consider:

* skeleton states
* optimistic interactions
* progressive rendering
* partial loading
* meaningful transitions
* immediate interaction feedback

Do not fake performance with misleading animations.

---

# Content

Design around real content whenever possible.

Do not use excessive placeholder text to fill layouts.

Consider:

* realistic names
* realistic lengths
* empty states
* long labels
* short labels
* missing images
* error messages
* large datasets

A design that only works with perfect placeholder content is not production-ready.

---

# Long Content

Test layouts with:

* long names
* long titles
* long descriptions
* translated text
* large numbers
* long email addresses

Do not assume every piece of content will fit into one line.

---

# Data Density

The appropriate density depends on the product.

For administrative systems:

```text
higher information density
```

may be appropriate.

For consumer applications:

```text
more whitespace
```

may improve comprehension.

Choose density according to:

* user goals
* frequency of use
* amount of information
* interaction complexity
* screen size

Do not maximize or minimize density automatically.

---

# Professionalism

A professional interface does not need to look expensive.

It needs to look intentional.

Professionalism often comes from:

* consistency
* restraint
* alignment
* typography
* spacing
* hierarchy
* predictable interactions
* polished states
* thoughtful details

Not from:

* more gradients
* more shadows
* more animations
* more cards
* more colors

---

# Design Before Implementation

Before implementing significant frontend UI, determine:

1. What is the primary user goal?
2. What information deserves the most attention?
3. What is the visual identity?
4. What are the primary colors?
5. What are the secondary colors?
6. What neutral colors support them?
7. What typography fits the product?
8. What geometry should define the interface?
9. What spacing system should be used?
10. What interactions require motion?
11. What components should be reusable?
12. What responsive behavior is required?
13. What accessibility considerations apply?

Do not immediately generate a large collection of components without establishing the visual system.

# Design Review

Before considering a screen complete, review:

## Hierarchy

* Is the most important information obvious?
* Is the primary action obvious?
* Are secondary elements appropriately quieter?

## Spacing

* Are related elements grouped?
* Is there enough breathing room?
* Is whitespace intentional?

## Color

* Are brand colors used strategically?
* Are neutrals doing enough work?
* Is contrast sufficient?

## Geometry

* Are radii consistent?
* Are rounded elements excessive?
* Does the geometry match the product?

## Typography

* Is the hierarchy clear?
* Are font sizes readable?
* Are weights used intentionally?

## Interaction

* Are hover states useful?
* Are focus states visible?
* Are active states clear?
* Does the UI respond immediately?

## Motion

* Is animation meaningful?
* Is it fast enough?
* Is it subtle enough?
* Is reduced motion supported?

## Responsive Design

* Does the interface work on mobile?
* Does it work on desktop?
* Does content remain readable?
* Are controls usable?

## Accessibility

* Is keyboard navigation possible?
* Is contrast sufficient?
* Are controls labeled?
* Are errors understandable?

# Anti-Pattern Checklist

Before finalizing a frontend design, check for:

* [ ] Too many rounded elements
* [ ] Too many pills
* [ ] Too many cards
* [ ] Cards nested inside cards
* [ ] Excessive gradients
* [ ] Excessive glass effects
* [ ] Excessive shadows
* [ ] Excessive glow
* [ ] Too many colors
* [ ] Weak typography hierarchy
* [ ] Poor spacing
* [ ] Poor alignment
* [ ] Everything competing for attention
* [ ] Excessive icons
* [ ] Decorative elements without purpose
* [ ] Unnecessary charts
* [ ] Unnecessary statistics
* [ ] Excessive animation
* [ ] Animations that are too slow
* [ ] Distracting hover effects
* [ ] Missing loading states
* [ ] Missing error states
* [ ] Missing empty states
* [ ] Missing focus states
* [ ] Mobile treated as an afterthought
* [ ] Accessibility problems
* [ ] Components created only because they look modern
* [ ] Visual patterns inconsistent between pages

If several of these are present, simplify.

# Final Simplification Pass

Before finishing, deliberately ask:

```text
What can be removed?
```

Then ask:

```text
What can be simplified?
```

Then:

```text
What needs stronger hierarchy?
```

Then:

```text
What interaction could feel smoother?
```

Then:

```text
What feels generic or AI-generated?
```

Remove unnecessary visual noise.

# Final Design Principles

When choosing between:

**more decoration**

and:

**better composition**

choose better composition.

When choosing between:

**more animation**

and:

**better interaction**

choose better interaction.

When choosing between:

**more components**

and:

**clearer hierarchy**

choose clearer hierarchy.

When choosing between:

**more colors**

and:

**better color relationships**

choose better color relationships.

When choosing between:

**more rounded elements**

and:

**better geometry**

choose better geometry.

When choosing between:

**a popular UI trend**

and:

**a design appropriate for the product**

choose the product.

When choosing between:

**visual complexity**

and:

**clarity**

choose clarity.

The final interface should feel:

**Sharp. Smooth. Clean. Intentional. Professional.**

It should look like someone made deliberate design decisions — not like an AI was simply asked to "make it modern."
